# vitapick 서비스 설계서

작성일: 2026-11-16 · 작성자: 이오리 · 단계: MVP 구현

## 목적과 범위

사용자의 식단 입력을 저장하고 공공 식품영양성분 데이터를 검색하여 100g 기준 영양 정보를 참고할 수 있도록 합니다. 매일의 합계 및 최근 7일 열량을 표시하며, 관리자에게 회원 목록과 권한 변경 기능을 제공합니다.

## 화면

| 화면 | 주요 기능 |
| --- | --- |
| 홈 | 브랜드 소개, 서비스 가치, 시작하기 |
| 로그인/회원가입 | 이메일/비밀번호, 공용 테스트 계정(일반/관리자), Google/Naver/Kakao OAuth |
| 대시보드 | 오늘의 영양 합계, 식단 요약, 리포트 안내 |
| 식단 기록 | AI 문장 기록(음식·구분·섭취량 분리) + 음식 검색, 기록 조회/삭제 |
| 영양 리포트 | 오늘의 목표 대비 섭취량, 최근 7일 열량, 신체 정보 기반 목표 계산, 회원 탈퇴 |
| 회원 관리 | 관리자 전용 목록, 권한 변경(일반 ↔ 테스트 관리자 ↔ 관리자), 회원 삭제 |

모바일 내비게이션은 오른쪽에서 열리는 드로어이며 배경 클릭 또는 닫기 버튼으로 닫습니다.

## 데이터 흐름

1. 사용자는 이메일 또는 제공자 OAuth로 로그인합니다. 비밀번호는 Argon2로 해싱하고 JWT는 12시간 동안 유효합니다. 프런트엔드는 토큰을 탭 단위 `sessionStorage`에 보관합니다.
2. 식단은 사용자 ID로 격리하여 DB에 저장합니다. API에서 인증/권한을 매 요청 검사하며, 본인 기록만 읽고 삭제할 수 있습니다.
3. 음식 검색 데이터는 공공데이터포털의 식품의약품안전처 식품영양성분DB정보 API(`FoodNtrCpntDbInfo03/getFoodNtrCpntDbInq03`)에서 가져옵니다. `serviceKey`와 페이지 번호를 전달해 g 단위의 유효한 행을 100g 기준으로 환산해 TiDB `foods` 테이블에 업서트합니다. S3는 사용하지 않습니다. 사용자가 섭취량에 맞게 영양값을 직접 조정한 뒤 저장합니다.
4. AI 문장 기록은 `POST /api/meals/parse`가 문장을 Gemini(구조화 출력, 실패·키 없음 시 한국어 규칙 분석기)로 음식·식사 구분·날짜·섭취량으로 분리하고, 각 항목을 `foods` 테이블과 매칭해 100g 기준값 × 섭취량으로 영양을 계산합니다. AI가 영양값을 생성하지 않습니다. 사용자당 10분 20회로 제한합니다.
5. 프런트엔드는 식단 레코드를 합산하여 오늘과 최근 7일을 시각화합니다. 프로필 미입력 시 목표값은 일반 성인 예시(열량 2,000kcal, 단백질 55g, 탄수화물 275g, 지방 70g)입니다. 입력 시 18세 이상 대상 Mifflin-St Jeor 기초대사량 공식과 활동계수(1.2~1.725)를 적용해 추정 열량을 산정하고 탄수화물 50%, 단백질 20%, 지방 30% 비율로 환산합니다. 이는 식이 처방이 아닌 참고 수치입니다.

## 스키마

- `users`: id, email(unique), name, password_hash(nullable), role, provider/provider_id(unique), created_at, age, biological_sex, height_cm, weight_kg, activity_level
- `meals`: id, user_id(FK), food_name, meal_type, eaten_at, serving_g, calories, protein, carbs, fat
- `foods`: id, source_id(unique), name, 100g당 열량/단백질/탄수화물/지방, updated_at
- `oauth_tickets`: 일회용 code_hash, user_id, expires_at(2분)

## API

`/api/auth/register`, `/login`, `/me` (GET/DELETE — 회원 탈퇴), `/demo-status`, `/demo-login`, `/oauth/{provider}/start`, `/oauth/{provider}/callback`, `/oauth/exchange`, `/oauth/providers`; `/api/nutrition/targets` (GET), `/api/nutrition/profile` (PATCH), `/api/meals` (GET/POST), `/api/meals/{id}` (DELETE), `/api/meals/parse` (POST) · `/api/meals/parse/status` (GET), `/api/foods?q=`, `/api/admin/users` (GET), `/api/admin/users/{id}/role` (PATCH), `/api/admin/users/{id}` (DELETE), `/api/health`.

## 보안 및 한계

- 운영 환경에서 `JWT_SECRET`/`DATABASE_URL`은 필수입니다. 공용 테스트 계정은 `DEMO_ACCOUNTS_ENABLED=true`일 때만 열리며, 테스트 관리자는 매 로그인 읽기 전용(`viewer`)으로 강제되어 실제 회원 정보가 마스킹된 목록만 볼 수 있고 모든 쓰기 요청은 서버가 거부합니다.
- 회원 탈퇴는 이메일 계정의 경우 비밀번호 재확인이 필요하며 식단·OAuth 티켓이 함께 삭제됩니다. 관리자의 회원 삭제는 본인·공용 테스트 계정·마지막 실제 관리자에게 적용되지 않습니다.
- OAuth는 검증된 이메일만 허용하고 이메일 일치만으로 기존 계정을 연결하지 않습니다. `state` 쿠키로 요청 위조를 방지하며 일회용 교환 코드로 백엔드 토큰을 전달합니다.
- 로그인 시도 제한, 이메일 인증/계정 복구, 개인정보 처리 및 데이터 보존 정책, 질환/임신/알레르기 등을 반영한 임상적 권장량 산정, 정교한 통계/머신러닝, 대규모 동기화 및 DB 마이그레이션은 후속 작업입니다. 현 단계의 리포트는 의료 서비스가 아닙니다.
- 초기 스키마는 SQLAlchemy `create_all`로 구성합니다. 운영 스키마 변경 전 Alembic 마이그레이션이 필요합니다.
