## 2. 프로젝트 배경 및 문제 정의 (Why)

**시각 자료**
- 좌: "기존 식단 앱" 사용자 여정 — 음식 검색 → 영양값 수동 입력 → 이탈 (이탈 지점에 빨간 표시)
- 우: 파편화된 데이터 — 식품안전나라 / 공공데이터포털 / 표준데이터가 서로 다른 형식으로 흩어진 그림

**본문**
- 문제 1. **입력 피로** — 영양값을 사용자가 직접 찾아 입력 → 기록 지속률 하락
- 문제 2. **데이터 파편화** — 공공 식품영양 데이터는 약 **34만 건**이지만 서비스마다 형식·인증 방식이 다름
- 문제 3. **획일적 목표** — "하루 2,000kcal"처럼 개인 차이를 반영하지 않는 기준
- 목표: 데이터 수집은 **자동화**, 목표는 **개인화**, 결과는 **한눈에**

**발표자 스크립트**
> 식단 앱을 써 보면 가장 먼저 지치는 지점이 영양값 입력입니다. 정작 국가가 관리하는 식품영양 데이터는 34만 건 넘게 공개돼 있는데, 출처마다 형식도 인증 방식도 달라서 일반 사용자가 쓰기 어렵습니다. 그리고 대부분 앱이 모든 사람에게 같은 2천 칼로리 기준을 보여 줍니다. 그래서 저는 세 가지를 목표로 잡았습니다. 데이터는 사람이 아니라 파이프라인이 모으고, 목표는 사용자의 신체 정보로 계산하고, 결과는 숫자가 아니라 한눈에 보이게 하자는 것입니다.

## 3. 서비스 핵심 가치 및 솔루션 (What)

**시각 자료**
- 3단 카드: ① 자동 동기화(DB 아이콘) ② 맞춤 목표(사람+수식 아이콘) ③ 건강 리포트(차트 아이콘)
- 각 카드 아래 실제 수치 배지

**본문**
- ① **공공데이터 자동 동기화** — 식품의약품안전처 식품영양성분DB API → TiDB, 매주 자동 실행 (현재 1,095개 식품 적재)
- ② **개인 맞춤 영양 목표** — 나이·성별·키·몸무게·활동량 → Mifflin-St Jeor 공식 기반 열량 + 탄·단·지 목표
- ③ **직관적 리포트** — 오늘의 목표 대비 진행률, 최근 7일 열량 추이, 상황별 케어 메시지
- 공통: 의료 진단이 아닌 **참고용 추정치**임을 화면마다 명시

**발표자 스크립트**
> healthpick의 핵심은 세 가지입니다. 첫째, 공공 식품영양 API를 주 1회 자동으로 수집해서 TiDB에 적재합니다. 지금 운영 DB에는 정제를 통과한 1,095개 식품이 들어 있습니다. 둘째, 사용자가 신체 정보를 입력하면 검증된 공식으로 개인별 열량과 3대 영양소 목표를 계산합니다. 셋째, 그 목표 대비 오늘과 지난 7일을 리포트로 보여 줍니다. 그리고 헬스케어 서비스인 만큼, 이 수치가 의료적 처방이 아니라는 고지를 모든 분석 화면에 넣었습니다.

## 4. 전체 시스템 아키텍처 (Architecture)

**시각 자료** (다이어그램)
```
[Browser]
   │  HTTPS (VITE_API_URL)
   ├─► Netlify (React 정적 빌드) ─┐
   └─► Render Static (React)  ───┤
                                 ▼
                    Render Web Service (Docker · FastAPI)
                      │ JWT 인증 · CORS 허용 목록 · OAuth
                      ▼  TLS (인증서 검증)
                    TiDB Cloud ─ healthpick DB (users · meals · foods · oauth_tickets)
                      ▲
   GitHub Actions (매주 월 cron + 수동) ─ rpa/sync_foods.py ─► 공공데이터포털 API
```

**본문**
- **3계층 분리** — 정적 프런트 / API 서버 / 관리형 DB
- **배치와 서비스 분리** — 데이터 수집은 API 서버가 아닌 GitHub Actions에서 실행 → 사용자 요청 처리에 영향 없음
- **프런트 이중 배포** — 같은 빌드를 Netlify·Render 양쪽에 배포, API는 하나 (CORS 허용 목록으로 출처 관리)
- **DB 연결은 TLS + 서버 인증서 검증** (`ssl.create_default_context`)

**발표자 스크립트**
> 구조는 세 덩어리입니다. React 정적 프런트는 Netlify와 Render 두 곳에 배포했고, 둘 다 Render에 Docker로 올린 FastAPI 하나를 호출합니다. DB는 TiDB Cloud를 씁니다. 제가 가장 신경 쓴 건 수집 배치를 API 서버에서 떼어 낸 것입니다. 34만 건을 페이지 단위로 긁는 작업이 무료 플랜 서버 안에서 돌면 사용자 요청이 느려지거나 서버가 재시작될 수 있어서, 배치는 GitHub Actions가 주 1회 실행하고 결과만 같은 DB에 쓰게 했습니다. DB 연결은 TLS로 하되, 인증서 검증을 끄지 않았습니다.

## 5. 기술 스택 선정 이유 (Tech Stack & Why)

**시각 자료**
- 표: 영역 / 선택 / 대안 / 선택 근거

**본문**
| 영역 | 선택 | 고려한 대안 | 선택 근거 |
| --- | --- | --- | --- |
| API | FastAPI + Pydantic | Flask, Django | 요청 검증을 타입으로 선언(범위·NaN 차단), 자동 문서(`/docs`) |
| DB | TiDB Cloud (MySQL 호환) | 로컬 SQLite, RDS | 개발·운영 **같은 DB 엔진**으로 환경 차이 제거, 서버리스 무료 티어 |
| ORM | SQLAlchemy 2.0 | 원시 SQL | 바인딩 파라미터로 SQL 인젝션 차단, 테스트 시 엔진 교체 용이 |
| 인증 | Argon2 + JWT(HS256) | bcrypt, 세션 | Argon2는 메모리 하드 해시, JWT는 프런트·API 분리 배포에 적합 |
| 프런트 | React 19 + Vite + Tailwind v4 | Next.js | 정적 호스팅만으로 배포 가능, SSR 불필요 |
| 수집 | requests (공식 API) | Playwright 크롤링 | 공식 API가 있으면 크롤링보다 안정적이고 이용 약관상 안전 |
| 테스트 | pytest + 인메모리 SQLite | 운영 DB 테스트 | 운영 데이터 오염 0, 실행 3초 |

**발표자 스크립트**
> 기술은 "익숙해서"가 아니라 문제 기준으로 골랐습니다. 가장 많이 받는 질문이 왜 로컬에서도 SQLite 대신 TiDB를 썼냐는 건데요, 로컬과 운영 DB 엔진이 다르면 운영에서만 터지는 버그가 생깁니다. 그래서 개발과 운영은 같은 TiDB를 쓰고, 테스트만 인메모리 SQLite로 격리해서 테스트가 운영 데이터를 절대 건드리지 못하게 했습니다. 수집에 Playwright를 쓰지 않은 것도 의도입니다. 공식 API가 있는데 화면을 긁으면 사이트 개편 한 번에 깨지고 약관 문제도 생깁니다. 그래서 API 우선으로 가고, 브라우저 자동화는 API가 없는 출처가 생길 때 도입할 계획입니다.

## 6. 핵심 기술 ①: 공공데이터 수집 파이프라인

**시각 자료**
- 파이프라인 흐름: `Extract(API 500건/페이지)` → `Validate(응답 코드·스키마)` → `Transform(100g 환산)` → `Load(일괄 upsert)`
- 정제 결과 막대: 원본 5,000행 → 적재 1,095행 (제외 사유: 탄수화물·지방 빈칸)

**본문**
- **Extract** — `FoodNtrCpntDbInfo03` API, `serviceKey` 쿼리 인증, 1회 최대 **500건** (1,000 요청 시 오류 코드 11 → 실측으로 확인)
- **Validate** — `resultCode == "00"` 아니면 즉시 실패, 응답 구조(`header` / `body.items`) 검사, 비정상 짧은 페이지 감지
- **Transform** — 1회 제공량 기준 → **100g 기준 환산**, g 단위만 채택(mL 제외), 빈값·NaN·음수 제외
- **Load** — 페이지 단위로 기존 행 한 번에 조회 후 upsert → **재실행해도 중복 0** (멱등성)
- **Schedule** — GitHub Actions 매주 월요일 + 수동 실행, 키는 Actions Secrets로 주입
- 보안 — 실패 메시지에 API 키가 섞이지 않도록 예외 내용 미출력

**발표자 스크립트**
> 파이프라인은 ETL 네 단계입니다. 공공데이터포털 API를 500건씩 페이지로 받는데, 이 500이라는 숫자는 문서가 아니라 실측으로 찾았습니다. 1,000건을 요청하니 오류 코드 11이 돌아와서 상한을 코드에 반영했습니다. 변환 단계에서 가장 중요한 결정은 빈값 처리였습니다. 원본 5,000행 중 상당수가 탄수화물이나 지방이 빈칸인데, 이걸 0으로 넣으면 그 음식은 지방이 0인 음식이 돼 버립니다. 영양 서비스에서 이건 틀린 정보이기 때문에 과감히 제외했고, 그 결과 1,095행만 적재했습니다. 적재는 같은 식품코드면 갱신하는 방식이라 몇 번을 다시 돌려도 중복이 생기지 않습니다.

## 7. 핵심 기술 ②: 맞춤형 영양소 분석 및 시각화

**시각 자료**
- 수식 박스 + 예시 계산
- 리포트 화면 캡처 (오늘의 영양 균형 막대 4개 + 최근 7일 열량 막대 차트)

**본문**
- **기초대사량 (Mifflin-St Jeor)** — `10×체중(kg) + 6.25×키(cm) − 5×나이 + (남 +5 / 여 −161)`
- **활동계수** — 1.2 / 1.375 / 1.55 / 1.725 (4단계) → 일일 에너지 추정, 10kcal 단위 반올림
- **3대 영양소 배분** — 탄수화물 50% · 단백질 20% · 지방 30% (÷4, ÷4, ÷9 kcal/g)
- 예시: 30세 여성, 165cm, 60kg, 가벼운 활동 → **1,820kcal** (테스트 코드로 검증)
- 입력 검증 — 18~100세, 키 100~230cm, 몸무게 30~300kg만 허용 (미성년자는 공식 적용 제외)
- 미입력 시 일반 성인 예시(2,000kcal)로 표시하고 "추정치" 고지
- **시각화** — 라이브러리 없이 React로 진행률 막대·7일 막대 차트 구현, `role="progressbar"`·`aria-label`로 스크린리더 지원

**발표자 스크립트**
> 개인 목표는 임상에서도 쓰는 Mifflin-St Jeor 공식으로 기초대사량을 구하고, 활동계수를 곱해 하루 필요 열량을 추정합니다. 예를 들어 30세 여성, 165센티, 60킬로, 가벼운 활동이면 1,820칼로리가 나오고, 이 값은 테스트 코드에 그대로 고정해 두었습니다. 공식이 성인 기준이라 18세 미만은 입력 자체를 막았습니다. 시각화는 Plotly 같은 라이브러리 대신 React로 직접 그렸습니다. 필요한 차트가 막대 두 종류뿐이라 수백 KB짜리 라이브러리를 넣을 이유가 없었고, 대신 진행률 막대에 접근성 속성을 넣어 스크린리더에서도 읽히게 했습니다.

## 8. 주요 기능 시연 ①: 사용자 인증 및 보안

**시각 자료**
- 로그인 화면 캡처 (좌: 브랜드 패널 / 우: 폼, 소셜 버튼, 테스트 계정 박스)
- OAuth 시퀀스 다이어그램: 브라우저 → API `/start`(state 쿠키) → 제공자 → `/callback`(state 검증) → 일회용 코드 → `/exchange` → JWT

**본문**
- **헬스 체크인 UI** — ECG 그리드 배경 · 바이탈 모니터 카드 / 로그인·회원가입 탭 · 원클릭 테스트 계정 2종
- **비밀번호 정책** — 영문 대·소문자 + 숫자 + 특수문자, 8~128자 (프런트·백엔드 이중 검증), Argon2 해시
- **OAuth 3종 (Google · Naver · Kakao)**
  - `state` 쿠키(HttpOnly, 10분)로 CSRF 방지
  - 토큰을 URL에 노출하지 않고 **2분짜리 일회용 교환 코드** 사용 (DB엔 SHA-256 해시만 저장)
  - **검증된 이메일만** 허용, 같은 이메일이어도 **기존 계정에 자동 연결하지 않음** (계정 탈취 방지)
- **원클릭 테스트 계정** — 일반 사용자 / 관리자, 환경 변수로 켜고 끔

**발표자 스크립트**
> 인증은 보안 결정이 가장 많이 들어간 부분입니다. 소셜 로그인 후 JWT를 그대로 URL에 붙여 돌려보내면 브라우저 기록이나 로그에 토큰이 남습니다. 그래서 2분 동안 한 번만 쓸 수 있는 교환 코드를 주고, 프런트가 그걸 API에 다시 보내 토큰을 받게 했습니다. DB에는 그 코드의 해시만 저장합니다. 또 하나는 이메일이 같다고 기존 계정에 자동으로 붙이지 않은 것입니다. 이걸 허용하면 남의 이메일로 만든 소셜 계정으로 기존 계정을 가로챌 수 있습니다. 면접관분들이 바로 써 보실 수 있게 테스트 계정 버튼도 넣었는데, 이건 관리자 슬라이드에서 보안 설계와 함께 다시 말씀드리겠습니다.

## 9. 주요 기능 시연 ②: 핵심 유저 플로우 (식단 기록 ~ 리포트)

**발표자 스크립트**
> 실제 사용 흐름입니다. 식단 기록에서 음식 이름을 두 글자 이상 치면 공공데이터에서 검색하고, 고르면 100그램 기준 영양값이 자동으로 채워집니다. 2장에서 말씀드린 입력 피로를 줄이는 부분입니다. 키 입력마다 API를 부르지 않도록 300밀리초 디바운스를 걸었습니다. 저장하면 대시보드와 리포트가 바로 갱신됩니다. 백엔드에서는 모든 식단 조회와 삭제에 본인 확인을 넣어서, 다른 사람의 기록 번호를 알아도 접근할 수 없고 존재 여부도 드러나지 않게 404를 돌려줍니다.

  - 운영에서 `JWT_SECRET`·`DATABASE_URL` 누락 시 **기동 거부** (안전하지 않은 기본값으로 뜨지 않음)
  - 브라우저에 포함되는 값은 공개 값인 `VITE_API_URL` 하나뿐

**발표자 스크립트**
> 배포는 프런트, 백엔드, 데이터 배치를 완전히 나눴습니다. 프런트 파일이 바뀌면 Netlify만, 백엔드 파일이 바뀌면 Render만 다시 빌드하고, 문서만 고친 커밋은 아무것도 재배포하지 않습니다. 데이터 수집은 GitHub Actions가 주간 스케줄로 돌립니다. 환경 변수는 로컬에선 .env 하나로 관리하고, 운영에는 각 플랫폼에 필요한 값만 넣습니다. 특히 운영에서 JWT 비밀키나 DB 주소가 빠지면 임시 값으로 조용히 뜨는 게 아니라 아예 기동을 거부하게 했습니다. 설정 실수가 보안 사고로 이어지지 않게 하려는 것입니다.

## 13. 트러블슈팅 (면접 핵심)

**시각 자료**
- 사례 3개를 `증상 → 원인 → 해결 → 재발 방지` 4칸 카드로

**사례 A. 프런트 배포가 전부 "취소"되고 404**
- 증상: GitHub 연동은 됐는데 사이트는 404, 배포 기록이 모두 `Canceled`
- 원인: 조건부 배포 규칙이 "이전 빌드 커밋과 비교해 변경 없으면 건너뜀"이었는데, Netlify는 **빌드 캐시가 없으면 이전 커밋 = 현재 커밋**으로 넘김 (공식 문서 명시) → 항상 "변경 없음"
- 해결: 두 값이 같으면 무조건 빌드하도록 조건 추가, 실제 커밋 3쌍으로 규칙을 로컬 재현 검증 → 푸시 약 1분 후 200

**사례 B. 공공데이터 API가 바뀌었다 — 인증·스키마·한도 전부**
- 증상: 식품안전나라 서비스가 공공데이터포털로 이관, 기존 수집 코드와 새 키가 맞지 않음
- 원인: URL 경로 인증 → `serviceKey` 쿼리 인증, 응답 구조 변경(`I2790.row` → `body.items`), 페이지 한도 1,000 → **500**
- 해결: 실제 응답을 먼저 찍어 스키마를 확인한 뒤 수집기 재작성, 인코딩된 키의 이중 인코딩 방지(`unquote`), 한도는 실측(1,000 요청 → 오류 코드 11)으로 확정, 목(mock) 응답 테스트 추가

**사례 C. "DB는 정상인데 운영 검색 결과가 0건" — 클러스터 혼선**
- 증상: 로컬 DB엔 데이터가 있는데 운영 API 검색 결과 0건
- 원인: TiDB 서버리스는 여러 클러스터가 **같은 게이트웨이 호스트**를 쓰고 사용자명 접두어로 구분 → 연결 문자열이 다른 클러스터를 가리킴
- 해결: `SHOW DATABASES`로 연결된 클러스터를 식별, **같은 검색어를 운영 API와 DB에 동시에 질의해 결과 수를 비교**하는 종단 간 검증으로 원인 확정 후 Render·Actions·로컬 연결 정보 통일
- 덤: 운영 서버가 `ADMIN_PASSWORD` 정책 위반으로 기동 실패 → 선택 기능 때문에 API 전체가 멈추지 않도록 "경고 후 건너뛰기"로 변경

**발표자 스크립트**
> 가장 많이 배운 건 배포 이후였습니다. 첫 번째, 프런트를 배포했는데 404가 나고 배포가 계속 취소됐습니다. 제가 넣은 "프런트 변경이 없으면 빌드하지 않는다"는 규칙이 원인이었는데, Netlify는 캐시가 없을 때 이전 커밋과 현재 커밋을 같은 값으로 넘깁니다. 그래서 규칙이 늘 "변경 없음"이라고 판단한 거죠. 문서로 원인을 확인하고, 실제 커밋 쌍으로 규칙을 재현해 검증한 뒤 고쳤습니다.
> 두 번째는 공공데이터 API가 포털로 이관되면서 인증 방식, 응답 구조, 페이지 한도가 한꺼번에 바뀐 일입니다. 추측으로 고치지 않고 실제 응답부터 찍어 보고 다시 짰습니다.
> 세 번째가 제일 기억에 남는데요, DB에는 데이터가 있는데 운영 검색은 0건이었습니다. TiDB는 여러 클러스터가 같은 호스트 주소를 써서, 연결 문자열이 다른 클러스터를 보고 있었습니다. 저는 같은 검색어를 운영 API와 DB에 동시에 던져 결과 개수를 비교하는 방식으로 원인을 확정했습니다. 이 경험으로 "배포 성공"과 "제대로 동작"은 다르다는 것, 그래서 끝에서 끝까지 검증해야 한다는 걸 배웠습니다.

## 15. 회고 및 향후 고도화 계획

**시각 자료**
- 좌: Keep / Problem / Try 3칸
- 우: 로드맵 타임라인 (단기 → 중기 → 장기)

**본문**
- **Keep** — 서버에서 강제하는 보안, 실측 기반 결정, 종단 간 검증 습관
- **Problem** — 배포 검증을 "HTTP 200"에서 멈췄다가 데이터 불일치를 늦게 발견 / 전체 약 34만 건 중 기본 설정(원본 5,000행) 범위만 동기화
- **Try (로드맵)**
  - 단기: `UPDATE_DATE` 파라미터 기반 증분 동기화, Alembic 마이그레이션, 로그인 시도 제한
  - 중기: pandas 기반 주간 영양 통계·이상치 탐지, 식품 검색 정확도 개선(전문 검색 인덱스)
  - 장기: 식단 사진 AI 인식(비전 모델), Docker 이미지 그대로 AWS(ECS) 이관

**발표자 스크립트**
> 잘한 점은 보안을 화면이 아니라 서버에서 강제한 것, 그리고 추측 대신 실측과 종단 간 검증으로 결정한 습관입니다. 아쉬운 점은 초반에 배포 검증을 HTTP 200에서 멈춰서 데이터가 엉뚱한 DB로 가는 걸 늦게 발견한 것입니다. 지금은 기본 설정으로 원본 5,000행 범위만 동기화하는데, 다음 단계로 API의 수정일 파라미터를 써서 바뀐 것만 가져오는 증분 동기화를 넣을 계획입니다. AI 문장 기록은 이미 Gemini로 구현해 운영 중이고, 장기적으로는 식단 사진 인식 같은 비전 기능으로 확장할 수 있습니다. 이미 Docker로 배포하고 있어서 AWS로 옮기는 비용도 낮습니다.

## 부록 A. 라이브 데모 시나리오 (3분 버전)

1. **사전 준비 (발표 10분 전)** — `healthpick-api.onrender.com/api/health`를 한 번 호출해 서버 깨우기 (무료 플랜 콜드 스타트 약 30초)
2. 로그인 화면 → 회원가입 탭에서 약한 비밀번호 입력 → 정책 오류 메시지 확인
3. **[일반 사용자]** 클릭 → 대시보드 → 식단 기록에서 음식명 2글자 검색 → 선택 → 저장 → 대시보드 진행률 변화

6. 로그아웃 → **[관리자]** → 회원 관리 → 실제 회원 마스킹 / 읽기 전용 안내(권한 변경·삭제 잠금) / 서버 403 확인

## 부록 B. 예상 질문과 답변 요점

| 질문 | 답변 요점 |
| --- | --- |
| RPA라고 했는데 크롤링은 어디 있나요? | 공식 API가 있어 크롤링을 하지 않았다. 안정성·약관 측면에서 API 우선, 스케줄 자동화는 GitHub Actions. 브라우저 자동화는 API 없는 출처에 한해 도입 계획 |
| JWT를 sessionStorage에 두면 XSS에 취약하지 않나요? | 맞다. 탭 종료 시 삭제되도록 sessionStorage를 택했고 React 기본 이스케이프로 XSS 표면을 줄였다. 다음 단계는 HttpOnly 쿠키 + CSRF 토큰 방식 전환 |
| 로그아웃해도 토큰이 12시간 유효하지 않나요? | 현재는 만료 시간에 의존한다. 리프레시 토큰 + 폐기 목록(또는 토큰 버전 컬럼)으로 개선 가능 |
| 34만 건 전체를 매주 받으면? | 500건 단위로 약 700페이지가 필요해 비효율적. `UPDATE_DATE` 기반 증분 동기화가 정답 |
| 빈 영양값을 제외하면 데이터가 너무 줄지 않나요? | 5,000행 중 1,095행. 양보다 정확성이 우선인 도메인. 대안은 "일부 정보 없음" 표시 후 포함하는 것 |
| 같은 식품을 두 배치가 동시에 쓰면? | `source_id` UNIQUE 제약이 최종 방어선. 배치는 주 1회 단일 실행이라 현실적 충돌 가능성은 낮음 |
| 테스트는 어떻게 했나요? | pytest 15개: 비밀번호 정책, 타인 데이터 접근 차단, RBAC, OAuth 코드 일회성·만료, 영양 공식, 수집 응답 검증·멱등 upsert, 관리자 초기화 실패 처리, 테스트 관리자 읽기 전용, 회원 탈퇴·관리자 삭제 보호 규칙, AI 문장 분석(규칙·Gemini·실패 대체). 인메모리 SQLite로 운영 DB와 격리 |
| 왜 TiDB인가요? MySQL이면 되지 않나요? | MySQL 호환이라 코드상 차이 없음. 관리형 서버리스 무료 티어 + 로컬·운영 동일 엔진이 선택 이유 |
| 프런트를 왜 두 군데 배포했나요? | Netlify(정적 CDN)와 Render 정적 사이트를 함께 운영. API는 하나이고 CORS 허용 목록으로 두 출처만 허용 |
| 의료 데이터 규제는? | 진단·처방이 아닌 참고용 추정치로 고지. 실제 서비스라면 개인정보 처리방침, 민감정보 동의, 보존 기간 정책이 필요 (향후 과제로 문서화) |
