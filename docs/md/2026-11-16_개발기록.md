- Netlify 예정 주소는 404, 구 Render 주소(`healthpick.onrender.com`)도 404. Blueprint 서비스 이름에 맞춘 `healthpick-api.onrender.com`은 긴 응답 지연으로 정상 동작을 확인하지 못함. GitHub 배포/체크 실행 내역 및 Actions secrets도 아직 없음. 대시보드의 Git 연동·실제 서비스 주소·환경 변수를 확인해야 함.
- 로컬 `.env`의 `FRONTEND_URL`은 Netlify 주소가 아니라 구 Render 주소를 가리킴. Render 대시보드에서는 `FRONTEND_URL=https://healthpick.netlify.app`, `BACKEND_URL`은 실제 Render 서비스 주소로 일치시키고, Netlify의 `VITE_API_URL`도 같은 API 주소로 설정해야 OAuth/CORS가 정상 동작함.
- 첫 수정 푸시 후 `healthpick-api.onrender.com/api/health`와 TiDB 기반 음식 검색은 HTTP 200을 반환했고 Google/Naver/Kakao 로그인 설정도 활성화됨. 그러나 Netlify 주소는 계속 404였으며 Render가 Netlify Origin의 CORS OPTIONS를 400으로 거부함. 의도된 Netlify 도메인을 API 허용 목록에 추가하고 회귀 테스트를 작성함.
- CORS 수정 푸시 후 Render OPTIONS는 HTTP 200 및 `Access-Control-Allow-Origin: https://healthpick.netlify.app`을 반환함. Netlify 홈과 로그인 경로는 45초 대기 후에도 404로, 사이트의 저장소 연결/배포 설정 확인이 남음. GitHub Actions의 `DATABASE_URL`/`MFDS_API_KEY` secrets도 등록되지 않아 예약 동기화는 아직 실행할 수 없음.
- 추가 확인: GitHub Actions에 `DATABASE_URL`과 `MFDS_API_KEY` 이름의 secrets 등록을 확인함(값은 조회하지 않음). 로컬의 발급 키로 공공데이터포털 `FoodNtrCpntDbInfo03` API 응답 코드 `00` 확인. 기존 식품안전나라 `I2790` 호출과 달리 포털은 `serviceKey` 쿼리와 `header`/`body.items` 형식을 사용하며, `numOfRows` 최대 500임(1000 요청 시 오류 코드 11). 수집기/테스트/문서를 이 형식으로 변경함. 전체 데이터는 약 34만 행으로 기본 10페이지는 일부만 가져옴.
- Render 프런트 `healthpick.onrender.com`과 API `healthpick-api.onrender.com`은 HTTP 200이며 Render 프런트의 API CORS 사전 요청도 200. Netlify 주소는 404. 사용자가 로컬 `render.yaml`의 `FRONTEND_URL`을 Render 프런트 주소로 변경했으므로 해당 변경을 보존함.
- 새 포털 API를 500건 단위로 읽어 첫 페이지 500행 중 483행의 g 단위 영양 데이터가 유효함을 확인. TiDB `foods`는 아직 0행이며 GitHub Actions 실행 기록은 없음. 실제 데이터 적재는 별도 실행 전까지 검증되지 않음. 현재 로컬 `.env`의 `ADMIN_PASSWORD`는 비밀번호 정책에 맞지 않아 로컬 API 시작 시 관리자 초기화 오류가 발생할 수 있음(값은 기록하지 않음).
